# Entry pages revamp: study

Date: 2026-10-04, Asia/Manila. Captures of the current pages: [1791115770_entry_pages_assets/](1791115770_entry_pages_assets/).

## Request

The human wants to revamp the design of the login and signup pages.

## Discovery answers (2026-10-04)

1. **How far.** "Branded entry": keep the app's dark look, and make these pages a proper front door with the mark, the product name, one line about what the app does, a full-width button and a tidier form. Not the louder "statement page" with a felt hero.
2. **Scope.** The whole entry flow: Log in, Sign up, "Sign-up needs an invite", and the "Join group" invite page.
3. **Additions.** Name the inviting group; shorter password rules; a show-password button.

## What exists today

Four templates share the narrow `form-page` frame (600 px, left-aligned):

| Page | Template | What it shows |
|---|---|---|
| Log in | `registration/login.html` | "Log in", username, password, a button at its text width, "No account? Sign up" |
| Sign up | `accounts/signup.html` | "Sign up", username with Django's stock help, password with a four-bullet rule list, "Password confirmation" with help, a button at its text width |
| Sign-up needs an invite | `accounts/signup_closed.html` | Two paragraphs and a "Log in" button; served with status 403 |
| Join group | `groups/invite_accept.html` | "Join {group}", one sentence, a full-width button; or an error notice |

Findings from the captures:

- **Nothing says what the app is.** A player who opens an invite link for the first time sees "Log in" and two fields. The mark appears only at 28 px in the header.
- **The primary button is the width of its text** on Log in and Sign up, unlike every other primary action in the app.
- **Sign up is dominated by help text.** Django's defaults: "Required. 150 characters or fewer. Letters, digits and @/./+/-/_ only.", four password bullets, "Enter the same password as before, for verification." On a 390 px phone the form is taller than the screen before any error.
- **The field label reads "Password confirmation".** Plainer: "Repeat password".
- **On desktop** the form is a 570 px column with wide fields and empty space below.
- **The invite is invisible.** On the live site sign-up needs an invite (`SIGNUP_REQUIRES_INVITE`). A newcomer follows `/join/<token>/`, is redirected to Log in with `?next=/join/<token>/`, and taps "Sign up". Neither page mentions the group they were invited to.
- **Existing precedent for a front door.** The first-group screen (`home-first` in `home.html`) already uses a 72 px mark, a 2 rem heading, one sentence and a form in a 440 px centred column. The entry pages can share that composition.

## How the flow works

- `accounts/views.py`: `signup` and `safe_next`. Log in is Django's `LoginView` with no extra context.
- `accounts/signup.py`: a registry `CHECKS`. `groups.access.invite_vouches(request, next_path)` resolves `next` to an `invite_accept` URL and checks the token with `services.usable_invite`. `accounts` does not import `groups` (app direction).
- Naming the group needs the same shape: a second registry in `accounts` that `groups` fills, returning the group name for a `next` path that is a usable invite. The token in the link is the secret; showing only the group name to its holder reveals nothing the link does not already grant.
- `SignupForm` is `UserCreationForm` with `username` only. Password rules come from `AUTH_PASSWORD_VALIDATORS` (similarity, minimum length 8, common password, not all numeric).
- Refused forms keep the username; passwords come back empty (DESIGN.md, "Account and supporting forms").
- There is no password reset (roadmap, Stage 5).

## Constraints

1. **Stack.** Django templates, plain CSS, small vanilla JavaScript modules. Everything must work without JavaScript.
2. **Design rules.** Dark, single column on phones, 48 px targets, visible focus, reduced motion, contrast of at least 4.5:1 (AGENTS.md rule 9, PRODUCT.md).
3. **Brand commitments** (PRODUCT.md). Plain, short words. No casino imagery. No invented claims: the one line about the app must state only what it does.
4. **Password managers.** Fields must keep `autocomplete="username"`, `current-password` and `new-password`, real labels and a normal form post. A show-password control must not change field names.
5. **No password reset exists.** Asking for the password once on Sign up would leave a mistyped password with no way back. The second field stays.
6. **Validators stay.** "Shorter password rules" changes the help text, not the rules. Django already reports the specific rule that a refused password broke.
7. **Security.** `next` stays validated by `safe_next`. The group name is shown only for an invite that is still usable. A wrong login keeps one message that does not say which field was wrong.
8. **Header.** `base.html` renders the site header on every page. With a large mark in the page body the header brand is a duplicate; the entry pages need a way to leave it out.
9. **Tests that pin the current markup.** `accounts/tests/test_auth.py`, `test_signup_gate.py`, `web/tests/test_remaining_design.py` and the browser scripts log in through `form.form-section button` and `[name=username]`. These selectors must keep working.

## Options considered

- **Statement page** (felt hero, two columns on desktop): declined by the human.
- **One password field with a show button**: rejected, constraint 5.
- **A separate landing page before Log in**: not asked for; the entry pages carry the one line about the app instead.
- **Keeping the site header and adding a second mark**: rejected as duplication; the entry pages drop the header brand and carry the lockup in the page.
